## 2. 链路修正（要求1，非 meta only）

**通用前置 + 平台管理用例链路**改为单一非 meta 路径，删除旧草稿的 Meta 数据源 `${sr_datasource2}`：

```
1) 控制台 · 公共管理 - 数据源中心：引入/新建 StarRocks 3.3.18 数据源 ${sr_ds}（JDBC，非 Meta 标识）
2) 数据源中心 · 应用授权：把 ${sr_ds} 授权给「数据资产」应用
3) 数据资产 · 平台管理 - 数据源管理：点「引入数据源」，引入 ${sr_ds}
4) 数据资产 · 平台管理 - 数据源管理：对 ${sr_ds} 执行「质量项目授权」，授权给质量项目 ${quality_project}
5) 数据质量各子模块即可选用 ${sr_ds}
```

只有走完 1→4，数据质量的数据源/库/表三级联动才能加载到 SR3.x。第 2 步「应用授权给数据资产」是旧草稿缺失、本次必须补的关键环。

## 4. 覆盖矩阵（要求3，粒度 A：每小规则 1 条富用例）

每个小规则 1 条富用例，组合走步骤内：

- **通过/不通过**：同条内 `校验通过 → 编辑改期望值 → 校验未通过`。
- **强/弱规则**：步骤内轮换（同一规则先弱后强，或不同小规则间交替覆盖）。
- **校验方法**：固定值 / 波动（环比/同比）按规则适用性轮换覆盖，不单独拆条。
- **单/多字段**：支持多字段的 6 个函数（#2 #3 #4 #5 #21 #22）各 +1 条多字段用例；其余仅单字段。
- **多表**：多表比对规则 + 自定义SQL 多表，各覆盖通过/不通过。
- **规则集**：导入规则包 → 运行，覆盖 1~2 条。

## 6. 测试数据策略

- **数据源**：SR 3.3.18（`${sr_ds}`），非 Meta，JDBC 引入。
- **建表语义**：证券交易域，主表 `zszq_trade_orders`（订单ID/证券代码/证券名称/交易类型/金额/价格/数量/日期/账户号），SR OLAP `DUPLICATE KEY` + `PARTITION BY RANGE(trade_date)` + `DISTRIBUTED BY HASH`。
- **多表比对/JOIN**：补副表（如 `zszq_trade_orders_mirror` 或维表 `zszq_account`）以驱动多表一致性比对与 JOIN 自定义SQL。
- **每条前置 SQL**：`DROP TABLE IF EXISTS` + `CREATE TABLE` + `INSERT`（含正常 + 针对该规则的异常行，驱动通过/不通过），可重入。
- **规范性数据**：身份证/手机号/邮箱列含合法 + 非法样本；数据精度/字符串长度列含越界样本。

## 8. case-draft 生成阶段必做的 live 核对项（陈旧风险兜底）

1. **规范性校验小规则真实集合**：字符串长度（vs 源码最大/最小长度）、数据精度、空值数、重复数 的真实 UI 文案与配置项；确认是否还有源码 2024 没有的新小规则。
2. **多表比对规则**：新建监控规则里的真实入口名称、配置项（关联键、比对字段、强弱）。
3. **各小规则在 SR3.x 上是否有可用 SQL 模板**：`assets_dq_function_template` 的 SR3 适配是 dev 交付物，可能存在「规则配置成功但运行报错」的真实缺陷——执行时如实记录，必要时转 defect-analyze。
4. **校验方法可选项**（固定值/波动 等）与各规则的适配关系。
5. **事实字段**：suite_name / prd_id(16035) / prd_version(7.0.0) / product_line / 目标版本目录，已知值见本文件头；缺口由 case-draft 按 skill 规则 AskUserQuestion 索要，不得编造。
