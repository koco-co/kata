# conflict-analyze

## 功能说明

分析源代码或文档的合并冲突，产出面向解决方案的冲突报告。不直接解决冲突，而是剖析冲突双方的意图和依据，给出可靠的解决路径建议。

## 输入

- **conflict** (required): 包含合并冲突标记的文本、文件或 diff。支持：
  - 包含 `<<<<<<<` / `=======` / `>>>>>>>` 标记的文件内容
  - 冲突文件路径
  - git merge 冲突状态
- **project** (optional): workspace ID。

**示例**:
```
"分析这个冲突文件: /path/to/conflicted-file.ts"
"帮我看看这个 PR 的冲突"
"以下文件有冲突，请分析: [粘贴冲突内容]"
```

## 输出

- **verdict**: 冲突分析结论——冲突双方各自的意图与依据。
- **remedy**: 解决方案建议——如何解决冲突的推荐方案。

## 执行流程

1. **冲突检测**：确认输入包含有效的合并冲突标记。
2. **双方分析**：
   - 解析 `<<<<<<<` 和 `=======` 之间的当前分支变更（ours）。
   - 解析 `=======` 和 `>>>>>>>` 之间的外来分支变更（theirs）。
   - 理解每段变更的意图和修改理由。
3. **冲突定性**：分析冲突类型（同一行修改/相邻行改动/语义冲突）。
4. **提出方案**：给出解决方案建议前，先陈述双方意图。
5. **输出报告**：生成 verdict + remedy 报告。

## 产物要求

### 报告结构

必须先陈述双方意图和依据，再给出解决方案：

```
## 冲突双方意图

- **当前分支 (ours)**: [变更内容] — [变更理由/依据]
- **外来分支 (theirs)**: [变更内容] — [变更理由/依据]

## 冲突分析

- 冲突类型: [同一行/相邻行/语义冲突]
- 影响范围: [影响的模块/功能]

## 解决方案建议

1. [方案一]: [说明]
2. [方案二]: [说明]
...
```

### 证据纪律

- 所有声明必须有冲突 diff 支持（`conflict.diff@1`）。
- 区分客观事实（代码变更内容）和主观推断（变更意图）。
- 方案建议必须是可执行的，不给出模糊或抽象的建议。

### 安全约束

- `workspace/{project}/.kata/repos/**` 为只读源仓库，冲突分析不修改任何仓库内容。
- `unsafe_resolution` 状态下产生 pending_items。
