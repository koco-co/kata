# knowledge-curate

## 功能说明

查询、更新与维护项目的业务知识、规则、术语、踩坑记录与模块事实。让项目的领域知识有统一的沉淀位置，避免知识碎片化。

**路由注意**: 用户询问"XX 是什么"（涉及项目特定业务概念）时，静默触发此 skill，用户不感知路由过程。

## 输入

- **query** (required): 用户的知识查询或维护请求。
- **project** (optional): workspace ID。

**示例**:
```
"数据质量模块的数据源类型有哪些？"
"记录一条规则：数据质量规则任务必须先配置规则集"
"什么是规则集管理？它和规则任务管理的关系是什么？"
"添加一条踩坑记录：Spark SQL 不允许全部分区字段"
```

## 输出

- **answer**: 对知识查询的回答（自然语言）。
- **entry**: 创建/更新的知识条目文件。

## 执行流程

### 查询流程

1. **query_or_stage_update**: 理解用户意图：查询还是写入？
2. **检索知识库**: 在 `workspace/{project}/knowledge/` 下搜索匹配条目。
3. **综合回答**: 结合检索结果和项目上下文给出答案。

### 写入流程

1. **query_or_stage_update**: 确认需要写入新知识。
2. **commit_knowledge_update**: 遵循知识库分类规约写入新条目。
3. **验证**: 确认条目写入正确位置。

## 产物要求

### 知识存放位置

- 项目知识统一存于 `workspace/{project}/knowledge/**` 之下。
- 未明确选定项目之前，不得跨项目编辑知识。

### 知识条目分类

知识条目应按以下维度分类：
- **业务规则**: 产品功能中的业务逻辑约束。
- **术语定义**: 项目特有的术语和缩写。
- **模块事实**: 各模块的结构、关系、能力边界。
- **踩坑记录**: 项目中遇到的技术/业务坑点及解决方案。
- **配置规范**: 环境、工具、依赖的最佳实践。

### 证据要求

- 每条知识条目需要 `knowledge.entry@1` 作为 SourceRef。
- 区分事实（已确认）、推断（合理推测）和假设（未验证）。
