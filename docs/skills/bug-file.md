# bug-file

## 功能说明

将可复现的运行时错误、控制台失败、堆栈跟踪、HTTP 错误等 bug 证据整理为结构化、可执行的 bug 报告。核心原则是"凡无证据者，一律不入文"——不虚构日志、负责人、模块或根因。

**路由注意**: 仅输入 ZenTao bug URL / bug-view URL / bug ID 时优先路由到 case-hotfix，而非此 skill。

## 输入

- **clue** (required): bug 证据，可以是：
  - 异常堆栈跟踪
  - 控制台错误输出
  - HTTP 错误响应
  - 截图/日志文件
  - 用户观察到的现象描述
  - 可复现步骤
- **project** (optional): workspace ID。

**示例**:
```
"控制台报错: TypeError: Cannot read properties of undefined"
"HTTP 500 错误: POST /api/data 返回 500"
"这个页面上传文件后没有反应"
"帮我记录这个 bug: /path/to/log.txt"
```

## 输出

- **report**: 结构化 bug 报告。包含四个必填部分：实际行为、预期行为、复现步骤、影响范围。格式可以是 Markdown 或 HTML（由 schema 表示）。

## 执行流程

1. **证据收集**：分析用户提供的所有证据（堆栈、日志、截图、描述等）。
2. **结构化整理**：将证据按四要素组织：
   - **实际行为（Actual）**：发生了什么错误？
   - **预期行为（Expected）**：正确情况下应该是什么？
   - **复现步骤（Steps）**：如何复现这个 bug？
   - **影响范围（Impact）**：影响了哪些模块/用户？
3. **证据标注**：标记每个声明的证据来源。
4. **报告输出**：生成完整的结构化 bug 报告。

## 产物要求

### 报告结构

bug 报告必须包含以下四个分项，不得合并：

| 字段 | 说明 |
|------|------|
| 实际行为 | 观察到的错误现象，必须有证据支撑 |
| 预期行为 | 正确的行为描述 |
| 复现步骤 | 可执行的步骤序列 |
| 影响范围 | 影响的模块、版本、用户范围 |

### 证据纪律

- 缺乏证据时，不得凭空虚构日志、负责人、模块或根因。
- 每个声明需要有对应的证据源引用（`bug.evidence@1`）。
- 区分观察事实与推断。

### 优先级建议

根据影响范围和建议复现条件给出优先级分类：
- **P0 (Critical)**: 阻塞核心功能
- **P1 (Major)**: 主要功能受影响
- **P2 (Minor)**: 边缘功能或 UI 问题
- **P3 (Trivial)**: 轻微问题
