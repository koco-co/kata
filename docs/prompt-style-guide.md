# kata 中文提示词风格指南

> 本指南是 kata 全项目提示词清通化改写的常驻依据，约 50 个文件的改写都对照它来做。
> 来源：`docs/superpowers/specs/2026-06-02-prompt-style-refactor-design.md` 第 3、4 节。

## 总纲

kata 的提示词大多来自 Codex 自我迭代，没经过人工校读就合入，日积月累攒下了一身翻译腔：工程黑话、中英混搭、文白夹杂。读起来别扭，跳转成本高，新读者得先在脑子里翻译一遍才看得懂。

这次改写只有一个目标：在不改变任何行为的前提下，把这些提示词写得读起来顺、模型也更好解析——像清通的现代汉语，而不是英语直译。

在指令型提示词里，「优雅」不靠华丽辞藻，而靠四件事：**干净、语序顺、有节奏、会留白**。这正是余光中《怎样改进英式中文》、思果《翻译研究》说的「清通」，也是这次唯一的文风基准。讲清通的文档，自己先得是清通中文的样板——所以这份指南本身也按下面的法则来写。

指南分五个部分，由表及里：

- **语言层（L1–L9）**——词与句，先把每个字眼说成人话。
- **结构层（S1–S7）**——句群与篇章，把意思理顺、把重复收掉。
- **排版层（P1–P5）**——空格、标点、标题，把版面规整。
- **保真红线（R1–R11）**——最高优先，凌驾于上面三层之上。
- **术语对照表**与**文件分类与处理策略**——改写时随手对照的两张速查表。

每条法则都用「编号 + 一句话法则 + 真实语料例子」的固定格式，方便改写时逐条对照查阅。例子里那些「原文 → 改写」的语料，是最有价值的部分，一个都别丢。

## 语言层（词与句）

先从最小的单位下手：把生造的术语、工程黑话、中英混搭，逐个换成日常说法。

- **L1 生造术语 / 黑话名词 → 日常词**
  分诊 → 按类型分流 · 对账 → 核对 · 门禁 → 检查项 · 管线 → 流程 · 不变量 → 铁律 · 回指 → 指回 · 归因 → 判断原因 · 可见编排 → 公开进度
  例：`事实性结论回指 evidence_refs` → `凡是结论，都要能指回 evidence_refs`

- **L2 工程黑话动词 → 说人话的动词**（与 L1 名词分开看）
  去重 → 去掉重复 · 反推映射 → 反向推出对应关系 · 归一 → 统一成 · 回写 → 写回 · 快照 → 存一份当时状态 · 落地 → 落实 / 写入 · 残留 → 留下的

- **L3 中英混搭 → 二分法**
  保留原文的：功能标识符（工具名 `AskUserQuestion` / `TodoWrite`、字段名、文件名、`§phase` 名、CLI `kata *`、产物名、schema 名）。译成中文的：可译的普通词（fork → 新开、Worker → 执行子代理、review → 评审、silent-mode → 静默模式）。混合短语逐 token 切分（`dry-run summary 数据源`：前半是契约要保真，后半译成中文）。
  例：`fork 一个 general-purpose 子代理执行扫描` → `新开一个 general-purpose 子代理来做扫描`

- **L4 翻译腔破折号因果 → 正面陈述 + 一短句说为什么**
  例：`无 self-run 结果不下成功结论——没跑过就说通过是假交付` → `没有跑过，就不能下「通过」结论。没跑就说通过，是假交付。`

- **L5 文白夹杂 / 酸腐凝练 → 主谓宾顺的白话**（「凡…者」「无…不…」、否定后置都要拆开）
  例：`凡无证据者一律不入文` → `没有证据的内容，一律不写进报告`
  例：`不带文件参数的全量重跑禁止` → `禁止用不带文件参数的全量重跑`

- **L6 抽象名词当主语 → 让人或具体物做主语**（余光中的核心主张）
  例：`失败处理先归类后动作` → `遇到失败，先判断它属于哪一类，再决定怎么处理`

- **L7 断尾无主语结论句 → 补主语或并入前句**
  例：`命中即可大幅缩短排查。` → `命中后能大幅缩短排查时间。`

- **L8 冗余双语注脚 → 删掉括号里的英文**（这里的英文不是标识符，纯装饰）
  例：`检索（lookup）`、`记录（record）` → `检索`、`记录`

- **L9「静默 X」系黑话 → 按语境分别译**，不要一刀切
  静默转发 → 不声张地转发 · 静默触发 → 自动触发 · 静默跳过 → 不吭声地略过义务（三者语义不同，要分别处理）

## 结构层（句群与篇章）

词理顺了，再往上一层看句子怎么排、篇章怎么组织：一句只说一件事，重复的话收成一处。

- **S1 一句塞太多约束 → 一句一意；长条件拆成「何时 → 怎么做」**
  （语料里最毒的一句在 `§5-plan-reconcile` 第 33 行：一句话塞了 6 个分支，要拆成「触发条件 + 触发动作」两块。）

- **S2 长枚举禁令堆成一句 → 改成 bullet 列表**，每个标识符逐个保真。

- **S3 括号里塞清单 / 机制解释 / 例外 → 外提成 bullet，或单独写一句「例外：…」**

- **S4 用符号拼接代替连词 → 散文里还原「和 / 或 / 则 / 就」**（`步骤=单页面`、`A + B`、`X → Y` 这类）；但样例与映射表里的符号是契约，不动。

- **S5 同义反复 / 相邻重复 → 合并**

- **S6 同一文件内多处近义重复（缺 DRY）→ 收敛成一处规范陈述，其余地方指回它**；每处的标识符都不能丢。

- **S7 同一概念多个名字并存 → 建术语对照表，全仓统一一遍**（Worker / 执行子代理、对账 / 核对、lint / 检查、subagent / Agent 这类）。

## 排版层

最后规整版面：空格、标点、标题，这些是全仓高频的机械项，统一一遍就能明显提升观感。

- **P1** 一段一意，主句放前面；列表项控制在一两行能读完，太长就拆。

- **P2** 中英文之间留一个空格（盘古之白）——全仓高频的机械项，统一规整。

- **P3** 中文标点用全角；英文直引号 `"…"` → 全角 `「…」`；西式破折号分隔的标题 `Title — Sub` 也规整（注意标题里的 skill 名、`§phase` 名是标识符，不动）。

- **P4** 标题本地化：英文小节标题（`Spec Reviewer Prompt`、`Hard-Rule Priority`、`Self-run command template`）译成中文；同一 skill 内章节标题的语言要保持一致。

- **P5** 章节骨架的黑话标题：`## 硬规则（不变量）` 这类跨文件复制的标题，整组**统一**换成同一个中文标题（如 `## 必须遵守的规则`），避免文件之间术语漂移。

## 保真红线 / 不可改清单

> **最高优先，凌驾于语言 / 结构 / 排版三层之上。**
> 任何改写法则一旦与下列红线冲突，红线优先。语序再顺、版面再漂亮，也不能以违反红线为代价。

- **R1 行为 / 语义零丢失**：所有阈值数字（如 `≤3 次修复`、`≤2 次重试`、`15 项门禁`、`keywords 6 段`）、触发条件、路由 / 改走目标、顺序依赖，都必须存活。

- **R2 标识符原样**：字段名、文件名、`§phase` 名、工具名、CLI（`kata *`）、产物名、schema 名（如 `PlanReconciliation@1`）、状态值（`aligned` / `plan_adjusted` / `blocked` / `source_backed_bootstrap` 等）、枚举值（category / severity）。

- **R3 frontmatter**：11 字段白名单不变；`description` 的触发关键词与改走目标**一字不动**（它是触发信号，动它有路由风险）；`argument-hint` / `model` / `effort` / `allowed-tools` 等也不动。

- **R4 格式契约不许散文化**：type/emoji 映射表、命令索引、产物矩阵、phase 枚举（`preflight|worktree|…`）、15 项门禁表、`keywords` 6 段规范、SQL/DDL 样例、JSON/YAML schema 样例——整块保真，只能碰它们之外的散文说明。**不得**借排版法则 P 或「表格只用于真正对照」之名去拆这些表。

- **R5 反例字符串零改写**：约束里作为反例的字符串原样保留，不要「规范化」。例如 `case-qa.md` 里的「不得把 sql 归一成 SQL」「不得把字段写成字段级」，以及占位反例文案「页面已存在数据」「已登录/具备权限」——一旦被自动规范化，断言的含义就被改坏了。

- **R6 被测关键字**：`case-qa.md` 顶部的 HTML 注释（被 `shared-case-qa.test.ts` 做存在性断言）、`project-workflow-rules.md` 的 KATA 通知模板字段名与 emoji 映射、`prompts/agent-*` 的 category / severity 枚举与 JSON 字段（被契约测试依赖）——散文里嵌着被测标识符，不动。

- **R7 代码块内的注释默认不动**，除非用户授权、且不改变示例语义。

- **R8 触发词与正文同词**：若某个词既是 `description` 触发词（`description` 因白名单不能改），正文就保持同一个词，不能只改一边，否则触发线索与正文术语会断裂。

- **R9 lint 行数上限不许破**：`SKILL.md ≤500`、`references ≤260`、`phases ≤260`。`cli-essentials.md`（251/260）只能等行或减行改写。

- **R10 同源重复块要同步**：`routing-guard.md` ↔ `CLAUDE.md` 的路由节、`project-workflow-rules.md` ↔ `git-workflow.md` ↔ `CLAUDE.md`、`infra-diagnose/SKILL.md` ↔ `ssh-protocol.md`、各 fewshot 副本——改一处就必须同步改所有副本，语义与关键术语对齐，避免措辞分叉。

- **R11** 只读源仓库规则不变；不加装饰性的契约标记（lint 禁止）；`§<数字>-<kebab>.md` 文件名不改（受 `PHASE_NAME_RE` 约束）。

## 术语对照表

全仓统一的词对（来自语言层 L1 / L2 / L3 与结构层 S7）。改写时凡遇左列写法，一律换成右列。同一概念全仓只用一个名字，不让它在文件之间漂移。

| 黑话 / 英文 | 统一中文 |
| --- | --- |
| 分诊 | 按类型分流 |
| 对账 | 核对 |
| 门禁 | 检查项 |
| 管线 | 流程 |
| 不变量 | 必须遵守的规则 |
| 回指 | 指回 |
| 归因 | 判断原因 |
| 可见编排 | 公开进度 |
| Worker | 执行子代理 |
| review | 评审 |
| silent-mode | 静默模式 |
| Healing（标题） | 自愈 |
| `## Contents`（英文标题） | `## 目录` |
| 去重 / 归一 / 回写 | 去掉重复 / 统一成 / 写回 |

> 注：这张术语对照表已据试点（计划 Task 1–2）复核锁定，全仓改写以此为准；`## 硬规则（不变量）` 这类整段英式标题统一改成 `## 必须遵守的规则`。

## 文件分类与处理策略

约 50 个文件按下面三类分别处理。分类越靠后，可改的余地越小、保真要求越高。三类都仍受保真红线（R1–R11）约束。

- **`prose-instruction`（纯散文指令，主战场，约 14 个）**：可以大胆重构章节、合并冗余、重排顺序，全面套用语言 / 结构 / 排版三层。仍受红线约束（标识符、触发词、阈值不动）。

- **`mixed`（散文 + 样例混合，约 29 个）**：改写前先**逐 token 标注**哪些是「可改散文区」、哪些是「不可改契约区」（代码块、表格、schema、枚举、映射）。只改散文说明和表格里的纯文案列；样例本体、围栏语言、字段名、符号全部保真。

- **`structured-format-or-sample`（结构化格式 / 样例，约 7 个）**：原则上只碰开头的散文导语，样例本体零改。这类文件的「行数」往往本身就是格式契约的一部分（如 `hotfix-archive-format.md` 的 SQL 写法、`§10-quality-gate.md` 的 15 项 check 名）。
