# kata 历史文件清理设计

**日期**：2026-07-10

**状态**：方向已确认，等待用户复核书面设计

## 目标

删除已经失效、重复或可以重新生成的文件，同时保留仍有业务价值的原始材料、用例、项目知识和运行记录。清理不能依靠目录名称猜测，也不能覆盖用户当前尚未提交的工作。

## 基本原则

1. 先盘点，再分类；
2. 先更新引用，再移动或删除；
3. 能从 Git 恢复的已提交文件不建立长期隔离副本；
4. 本次改造不删除主工作树中的未提交文件；
5. 格式调整、内容修正、结构迁移和删除分别提交；
6. 每项删除都能说明原因、新位置或替代内容；
7. 清理后增加自动检查，避免同类文件重新进入仓库。

分类按“待确认 → 保留 → 迁移后删除 → 可以直接删除”的顺序判断。只要路径在当前主工作树中有修改、删除或未跟踪状态，就直接进入待确认；即使它是 `.DS_Store` 或通常可删除的缓存，也不能被后续规则覆盖。

## 分类

### 保留

- 根级 `skills/` 中仍在使用的 Skill、脚本、模板和参考资料；
- 各平台仍需要的 manifest、hook、extension 和打包脚本；
- PRD、用例、metadata、原始输入和项目知识；
- 无法重新生成的重要截图、报告和现场记录；
- 最近一次有效运行的结果、Handoff 和必要附件；
- 仍被当前文档、测试或交付说明引用的文件。

### 迁移后删除

- `.claude/skills` 中迁到根级 `skills/` 的内容；
- `.agents/skills`、`.reasonix/skills` 等旧软链树；
- 固定名称的 `archive.md` 与 `cases.xmind`；
- 旧 CLI 命令、旧 schema 和旧运行目录；
- 已经合并到公共位置的重复提示词和规则；
- 仍被使用但存放位置不合适的文档；
- 需要先转换 metadata 或链接的历史用例。

这些文件只有在新位置可用、引用已经更新且检查通过后才能删除。

### 可以直接删除

- `.DS_Store`；
- 临时缓存、运行锁、编译缓存和普通日志；
- 可由已保留的原始压缩包完整重新解压的重复目录；
- 可以从原始结果重新生成的重复 HTML 报告；
- 内容已并入正式文件的 `.bak`、副本和旧草稿；
- 指向已删除内容的空目录与失效软链；
- 迁移完成后的旧平台适配副本。

“直接删除”仍需要经过引用检查，并写入清理记录。

### 待确认

- 无法判断是否仍有业务价值的历史用例；
- PRD、页面和源码互相不一致的内容；
- 当前主工作树中用户修改、删除或新建的文件；
- 唯一的一份失败现场、截图或运行结果；
- 无法判断压缩包与解压目录哪一份才是原始材料的情况；
- 文件名像备份，但内容尚未并入当前文件的情况；
- 既无公开入口，也未被引用，且没有测试用途的脚本；动态调用或人工运维用途无法排除时同样进入本类。

待确认文件不移动、不改写、不删除。

## 清理记录

预览计划写入 `docs/migrations/kata-v4/cleanup-plan.json`，执行结果写入同目录的 `cleanup-report.json` 与 `cleanup-report.md`。每项迁移或删除记录：

```text
原路径
处理方式
处理原因
新路径或替代内容
引用检查结果
对应提交
```

清理命令同时支持文本与 JSON 输出。JSON 可以被后续检查读取，Markdown 供人工复核。

## 引用检查

删除前检查：

- TypeScript、JavaScript、Python 和 Shell 的导入或调用；
- Markdown 链接与相对路径；
- Skill 的文件加载说明；
- CLI help 和示例；
- schema、metadata 和模板；
- symlink 目标；
- package、plugin 和 runtime manifest；
- 测试 fixture 与快照；
- `workspace/**` 内跨目录引用。

找不到引用不等于一定无用。原始材料、唯一运行记录和用户文件仍按前述分类处理。

## 运行历史

每个 `<feature>/` 功能目录至少保留最近一次有效运行的：

- `run.json`；
- `result.json`；
- `handoff.json` 与 `handoff.md`；
- 必要截图、trace 或报告附件。

中间失败、重复重跑和可以重新生成的 Allure HTML 可以删除。删除 `allure-results` 前，需要确认最终结果和必要附件已经保留，且现有文档没有继续引用原始数据。

过去分散在 `_shared/published-reports/`、`<feature>/runs/<自由命名目录>/` 和带年月分层目录中的文件，先迁到 `<feature>/runs/<run-id>/`，再按上述规则精简。

运行结果不按“只保留通过”简单处理。唯一能够说明产品问题的失败运行需要保留，直到问题关闭或内容已经整理到正式报告。

## 压缩包与解压目录

同一材料同时存在 ZIP 和解压目录时：

- ZIP 是用户提供的原始材料：保留 ZIP，处理完成后删除可重新解压的副本；
- ZIP 是项目生成的交付包：保留最终交付包和生成说明，删除重复中间目录；
- 解压目录中存在额外修改：先核对并合并，不能直接删除；
- 无法判断时进入待确认清单。

## 备份与历史副本

普通 `.bak`、`copy`、`old`、带时间戳的重复文件不作为长期历史保存方式。先比较内容：

- 当前文件已经包含全部有效内容：删除副本；
- 副本仍有独有内容：先合并或记录，再删除；
- 需要长期保留修改历史：使用 Git，而不是继续增加文件副本。

## `.gitignore`

需要重新检查根目录和 `workspace/**` 内的 `.gitignore`：

- 不得忽略需要保存的项目知识、配置和正式交付文件；
- 运行产物只能出现在统一 `runs/`；
- `.DS_Store`、缓存、锁、普通日志和临时解压目录始终忽略；
- 不允许一个宽泛规则同时隐藏临时文件和正式资料；
- 修改 ignore 前先检查已经被跟踪的文件，避免误以为加入规则就完成清理。

## 清理命令

公共 CLI 提供：

```text
kata workspace clean --dry-run
kata workspace clean --dry-run --format json
kata workspace clean --plan docs/migrations/kata-v4/cleanup-plan.json
kata workspace clean --apply docs/migrations/kata-v4/cleanup-plan.json
kata workspace check
```

`clean --dry-run` 只向终端输出分类、引用和计划动作，不写文件。`clean --plan <path>` 只写计划，不迁移或删除内容。计划保存基准 commit、主工作树已有改动清单，以及每个目标的路径、类型、SHA-256、分类、原因、引用结果和预定动作。

正式清理只接受 `--apply <plan>`。执行前重新核对基准 commit、主工作树已有改动、目标类型和 SHA-256；任一内容变化就整体停止，不重新扫描后继续删除。待确认项始终跳过。没有 `--apply` 时，命令不得迁移或删除文件。

删除命令不得通过模糊通配符覆盖整个 `workspace/**`。每个动作使用计划中的明确路径。

## 提交顺序

1. 清理工具、分类规则和测试；
2. Skill 与 CLI 路径迁移；
3. 用例文件和 metadata 迁移；
4. 运行历史整理；
5. 备份、重复文件和临时文件删除；
6. `.gitignore` 修正；
7. 长期检查加入 CI。

每个提交只处理一个主题。删除提交不得混入提示词重写或大规模格式化。

## 长期检查

CI 需要阻止：

- `.DS_Store`、普通 `.bak`、缓存和运行锁被提交；
- 运行产物出现在统一 `runs/` 之外；
- 失效的链接、导入和 symlink；
- 已删除 CLI 和旧目录重新出现；
- 多个平台重新保存业务 Skill 正文；
- 既无公开入口，也未被引用，且没有测试用途的新脚本；
- `.gitignore` 隐藏项目知识或正式交付文件。

## 安全边界

- 所有实施在隔离 worktree 中完成；
- 当前主工作树已有的删除、修改和未跟踪文件不进入自动清理；
- 删除前保存 `git status` 和清理预览；
- 已跟踪文件的删除只通过独立 Git 提交保存历史，不建立长期隔离目录；
- 清理后复核 `git status`、引用、插件打包和完整测试；
- 无法确认的文件宁可暂留，也不能凭文件名判断其价值。

## 完成标准

- 清理记录覆盖全部迁移和删除动作；
- 旧 Skill 目录、软链树、旧命令和旧产物路径已经移除；
- 正式资料、项目知识和必要运行记录仍可读取；
- 没有失效引用、导入或 symlink；
- `.gitignore` 不再混淆临时文件和正式资料；
- 当前用户未提交的文件没有被修改；
- 正式执行的路径、摘要和动作与用户复核的预览计划完全一致；
- `kata workspace check` 和完整项目检查退出 0；
- 清理后的 Codex 插件仍能安装并完成真实调用。
