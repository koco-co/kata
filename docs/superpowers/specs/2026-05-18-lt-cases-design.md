## 一级用例筛选标准（Task 1）

每个需求保留 **1-3 条** 候选用例（共约 100-150 行）：

1. **优先级**：仅取 P1
2. **主流程动词**：标题包含「新建/创建/配置/展示/列表/校验/启动/调度/导入/导出/生成/发布」等核心动作
3. **步骤覆盖**：步骤数 ≥ 3（避免纯 UI Check / 交互项）
4. **避开支线**：标题不含「异常 / 边界 / 非法 / 重复 / 校验失败 / 缺省」等支线场景关键词
5. **冲突时**：同需求多条候选符合，优先选步骤数最多的（覆盖度最高）

筛选输出为候选表格，由用户逐行拍板（yes / no / 替换为指定用例 ID）。

## katacli 改造（Task 3）

### 现状

`kata history-convert` 当前默认每需求一份独立 Archive MD（`per-feature` 行为）。

### 新增

1. 新增 `--mode <per-feature|merged>` 参数，默认 `per-feature`（行为不变）
2. `merged` 模式：
   - 输入：多份 CSV（如整个 ltqc 目录）
   - 输出：单一 MD 文件
   - 结构：
     - `# {title}`（一级，由 `--title` 参数指定）
     - `## v6.4.x`（二级，迭代版本）
     - `### {需求名}`（三级，保留 CSV iteration ID）
     - `##### 【Px】{用例标题}`（五级）
     - `> 前置条件` + `> 用例步骤` 表（同 Markdown 结构约定）
3. 新增 `--include-paths <file>` 参数，按需求模块路径白名单过滤
   - 文件格式：每行一个完整模块路径，例如 `/版本迭代测试用例/v6.4.3/元数据、数据质量支持doris3.x(#9346)`
4. 新增 `--priority <P1|P1,P2|all>` 参数，控制保留的优先级（默认 `all`）
5. 单元测试覆盖：合并模式输出结构、白名单过滤、空 CSV 输入边界

### 向后兼容

- 不传 `--mode` 时默认 `per-feature`，所有现有调用方行为不变
- 现有 `--filter <keyword>` 参数继续可用，与 `--include-paths` 互斥

## 新鲜度核查（过期用例处理）

用户强调「所有用例都要是最新的，历史迭代用例如果没更新就不能用，特别是数据质量」。处理机制：

1. **候选表格新增一列**「新鲜度风险」，自动标注以下规则触发的高风险用例：
   - 步骤/预期中出现旧菜单名（如「质量任务管理」→ 现在叫「规则任务管理」，参考 #10221 菜单名称修改）
   - 步骤/预期中涉及已下线/重构的功能点（参考 v6.4.8+ 的菜单/字段变更需求）
   - 涉及"质量报告"等版本演进频繁的模块
2. **交叉比对**：与现有 `archive.md` 中已有的主流程数据质量段（561 行起）做名词对比，新旧术语不一致的用例标记
3. **用户人工核对**：Phase 1 候选表格阶段，由用户在「你的决策」列对高风险项确认是否需调整步骤后再纳入
4. **Phase 3 校对**：主流程补强阶段，最终用例步骤与现有 archive.md 主流程对齐（菜单名、按钮名、字段名一致）

## 风险与边界

- **xmind 覆写**：必须保留原有非空模块（资产盘点 / 元数据 / 数据安全 / 平台管理 / 元数据质量 / 订阅的数据 / 数据标准非落标检查子节点等），只动 9 个空叶子和必要的中间结构
- **启发式筛选偏差**：自动筛选可能选错重点，候选表格阶段由用户纠偏
- **`merged` 模式兼容性**：默认 `per-feature` 保持原有调用方行为不变
- **新鲜度判断不可全自动**：步骤过期主要靠用户在候选表格阶段人工确认，启发式仅辅助标红
