# 岚图主流程用例重建与统一整理 — 设计

- 日期：2026-05-20
- Feature：`workspace/dataAssets/features/2099-01-lt-dq-smoke`
- 状态：已与用户对齐，待复核

## 1. 背景与问题

两份预交付文档由 `tmp/` 下一批分散的 codex 临时脚本从禅道导出的 CSV 抽取生成：

- **A = `岚图主流程用例整理.md` / `.xmind`**：岚图定制版**跨模块主流程回归集**，按产品模块横向组织（资产盘点 / 元数据 / 数据标准 / 数据模型 / 数据质量 / 数据安全 / 平台管理），共 460 条。其中**数据质量模块仅 45 条**。
- **B = `岚图已上线需求主流程用例.md` / `.xmind`**：岚图**已上线需求（数据质量域 49 个迭代需求）的追溯全量集**，按 `## 版本 / ### 需求 / ##### 用例` 纵向组织，共 1180 条。

源头是 `assets-csv/*.csv`（禅道导出，24 列，v642–v6410 九个版本文件，含跨版本重复）。岚图相关需求 = B 文档里的 49 个三级标题（需求）。

### 已确认的根因

用户列出的 1–4 号问题根因一致——**CSV→md 抽取的系统性缺陷**，且都落在 B 文档：

- CSV 中「步骤」「预期」各是单元格内的**编号列表**，按序号配对。抽取脚本把编号列表拆成表格行时，被步骤文本里的 `<` `>` 符号打乱，导致**丢行 + 步骤/预期错位**。
  - 实证（B 文档 Doris 3.x 报告查询用例）：CSV 正确为 `点击"<"→向前翻页` / `点击">"→向后翻页` / `切换每页展示数量→每页展示记录数为切换后的数量`；B 抽取后第 6–8 步丢了「点击">"」整行并错位。
- 其它系统性问题：跨版本重复（如 v643 与 v649 同一条）、标题冗余前缀（`数据质量 质量报告 验证…`）、旧菜单名残留、空预期单元格、需求名转换时丢数据源 token。

XMind 侧：`tmp/normalize-final-xmind.py` 把**所有优先级 marker 强制改成 `priority-1`**（抹掉 P1/P2/P3 区分），并存在 `<br>` 残留、配置项挤行等可读性问题。官方 `kata xmind-gen` 对「版本作二级标题」的多版本结构不适配，且本任务是一次性临时整理，故**不采用官方工具**，改为整合自定义脚本。

## 2. 目标

1. 两份文档（md + xmind）**内容最新、可读性强、可执行性强**。
2. **集中统一修复**抽取类缺陷，而非逐条手补。
3. A 的数据质量模块**覆盖全部 49 需求的主流程子集**（约 150–300 条，规则任务管理 / 规则集管理 / 数据质量报告等重点子模块多取）。
4. **统一所有用例格式**到 kata skill 用例规范（脚本处理 + 人工批量复查）。
5. 整合 `tmp/` 散乱脚本为一条带测试的管道。

## 3. 范围决策（已与用户确认）

| 决策点 | 结论 |
|---|---|
| 两份文档角色 | A = 跨模块回归主流程；B = 数据质量需求追溯全量。两者都交付。 |
| A 数据质量富化 | 覆盖全部 49 需求的主流程子集；重点子模块多取。 |
| A 其余 6 模块 | 保留现有内容，仅做格式统一 + bug 扫描，**不**从 CSV 重抽。 |
| B 修复策略 | 从 CSV 用修正后的解析器**整体重抽**，保留已有语义挑选，再叠加人工复查。 |
| XMind 生成 | 保留**自定义脚本**（修掉 marker bug 与可读性），不使用官方 `kata xmind-gen`。 |
| 需求标题 `(#id)` | 仅管道内部用于去重/挑选映射；**渲染进 md/xmind 时一律去掉**。 |
| tmp 收尾 | 整合成一条管道脚本；删除可重生中间产物；**所有临时产物（脚本/配置/工作文件）留在 `tmp/`**，交付物留 feature 根目录。 |

## 4. 管道架构

```
assets-csv/*.csv ──[extract]──► 规范化用例模型(JSON,内存) ──[render]──► A.md / B.md ──[xmind]──► A.xmind / B.xmind
   (唯一真源)        去重/改名/配对/前置          (中间态,不落盘)        (交付)               (交付)
                          ▲                                            ▲
        selection/b-select.yaml + selection/a-dq-pick.yaml      人工批量复查
```

- CSV 是唯一真源。A 的数据质量 + 整个 B 从 CSV 重抽；A 其余 6 模块沿用现有 md（仅格式归一 + bug 扫描）。
- 管道**幂等可复现**；挑选意图固化进受版本控制的 `tmp/selection/*.yaml`。

### 规范化用例模型

```
{ version, requirement_id, requirement_name, module, submodule,
  title, priority, preconditions: str, steps: [{idx, step, expected}] }
```

`requirement_id` 仅内部使用，不进渲染输出。

### 抽取规则（根治列错位）

- 步骤、预期各按 CSV 单格内**编号列表**解析，**按序号配对**（step N ↔ expected N）；不再用易被 `<`/`>` 打乱的拆分逻辑。
- `<` `>` `"` 等字符安全处理；单元格内换行 → `<br>`。
- 步骤数 ≠ 预期数时记为告警，进入人工复查清单。

### 跨版本去重 + 标题/菜单归一

- 去重：按 `(归一标题, 步骤指纹)` 去重，保留信息最全的一条。
- 去冗余前缀：剥掉标题里的模块/页面前缀。
- 菜单改名（token 级、带上下文保护）：`概览→总览`、`规则任务配置→规则任务管理`、`任务实例查询→校验结果查询`、`质量报告→数据质量报告`（注意不要误改「质量报告管理」等更长串）。

## 5. 格式规范（统一所有用例）

以 kata skill 规范为准：`.ai/core/skills/case-edit/references/archive-xmind-sync.md` + `CLAUDE.md`「Case Artifact QA」+ `tmp/style-guide.md`（LTQC 具体化）。强制项：

- 单用例模板：`##### 【Px】标题` → `> 前置条件`（单个无语言标签 ``` 块）→ `> 用例步骤`（`| 编号 | 步骤 | 预期 |` 三列）。
- 前置条件必含：账号/角色、数据资源（数据源 + 类型 + 库表 DDL/DML）、上游依赖、系统配置；不适用写「无」。
- 步骤 = 一行一原子动作；菜单路径统一 `【数据资产】→【数据质量】→【…】`；控件类型 + 文本 + `${变量}`。
- 预期：每观察项一行，多项用 `<br>1) <br>2)`，禁止挤一格；文案断言加引号。

## 6. 缺陷的集中统一修复

写成可复用规则 + 全量扫描，而非逐条手补：

| 用户问题 | 根因类别 | 统一规则 |
|---|---|---|
| #1 Doris 报告查询错位 | 列错位/丢行/`<>` 吞字 | 按序号配对重抽 + 字符处理（已验证根治） |
| #2 导入标准第一步无预期 | 空预期单元格 | 扫描所有空预期：能从 CSV 补则补，否则按动作类型补默认（操作类 → 「操作成功」） |
| #3 报告状态筛选 预期写反 | 语义错误（脚本扫不出） | 列入人工批量复查清单，逐条对照 CSV 修正（生成成功 → 生成失败） |
| #4 动态分区 hive 数据源转换后只剩一个 | 需求名转换丢数据源 token | 扫描标题/需求名转换前后数据源 token，缺失则回填（sparkThrift/hive 都保留） |

扫描器额外覆盖：空步骤行、步骤数 ≠ 预期数、残留旧菜单名、xmind 残留 `<br>`、`「…」` 三项挤一行。

## 7. 规则任务管理强前置（业务规则）

依据 `tmp/ruleset-prerequisite.md`：凡步骤含「新建监控规则 / 创建规则任务 / 配置监控规则」且无「导入规则包」环节的——

1. 前置条件追加「先在【规则集管理】创建规则集 `${rs_name}`（数据表 `${tableName}`）/ 规则包 `${pkg_name}`」。
2. 步骤升级为显式四步：基础信息 → 导入规则包 → 调度属性 → 保存。

例外：本身就测规则集功能的用例（如「验证规则集详情数据正确」）不改写。

## 10. 校验 + 人工批量复查 + 测试

- **自动校验器**（增强自 `tmp/validate-staging.py`）：frontmatter `case_count` 一致、A/B 与各自 xmind 逐字段一致、marker 分布、无占位符（TODO/待补充/待确认/FIXME）、无残留旧菜单、§6 扫描器全过。
- **人工批量复查**：管道跑完后，按子模块分批人工通读，重点抓脚本扫不出的语义错误（如 #3）；不依赖用户发现格式/业务缺陷。
- **测试**：`tmp/test_pipeline.py` 覆盖按序号配对、`<>` 处理、去重、改名、前置升级、空预期补全、marker 映射。改动后即跑受影响范围的测试。

## 12. 风险与开放点

- A 的 6 个非 DQ 模块只过格式归一 + bug 扫描，若它们也有抽取类缺陷只能被扫描器覆盖到的部分发现。
- 人工批量复查 1180 + ~600 条工作量大，需分批进行；语义类错误（如 #3）依赖人工判断。
- 去重时「保留信息最全的一条」的判定需谨慎，避免丢弃含特有步骤的版本。
