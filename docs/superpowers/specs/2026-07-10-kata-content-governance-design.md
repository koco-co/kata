# kata 格式与内容治理设计

**日期**：2026-07-10  
**状态**：设计已确认

## 目标

让源码、Skill、提示词、配置、用例和项目知识使用稳定的文件格式与自然、准确的中文。治理范围包括 `workspace/**`，但不自动修改用户尚未提交的本地文件。

格式调整和内容修正是两件事。它们使用不同命令、不同报告和不同提交，避免把机械排版与业务含义混在一起。

## 范围

默认处理 Git 已跟踪的文件：

- TypeScript、JavaScript、JSON 和 JSONC；
- Markdown、MDX、YAML、CSS、SCSS、HTML 和 Handlebars；
- Python；
- Shell；
- XML 与 JMX；
- Skill、prompt、reference、规则、README 和生成模板；
- `workspace/**` 中的 PRD、用例、metadata、项目知识、自动化脚本和文本报告。

未跟踪文件只进入清单，不自动格式化、改写或删除。实施者需要用户明确同意后，才能把它们加入范围。

## 工具

工具版本固定在项目依赖中，不能依赖 `bunx` 临时下载不同版本。

| 文件 | 工具 | 作用 |
| --- | --- | --- |
| TypeScript、JavaScript、JSON | Biome | 格式、导入和静态检查 |
| Markdown、YAML、CSS、HTML、Handlebars | Prettier | 稳定排版 |
| Markdown | Markdownlint | 标题、列表、链接、代码块等结构 |
| Python | Ruff | 格式和静态检查 |
| Shell | shfmt、ShellCheck | 排版和常见错误 |
| XML、JMX | XML 解析器与格式器 | 解析、编码和缩进 |
| XMind、PDF、图片、ZIP | 对应解析工具 | 确认文件完整、可以打开 |

二进制文件不做文本格式化。检查失败时报告文件和原因，不尝试猜测修复。

## 基础格式

全仓统一：

- UTF-8；
- LF 换行；
- 不使用 BOM；
- 文件末尾保留一个换行；
- 删除行尾空格；
- Unicode 使用 NFC；
- Markdown 标题、列表、表格和代码块保持一致；
- YAML、JSON 与代码使用项目约定的稳定缩进；
- 格式化命令连续执行两次时，第二次不再产生变化。

新增 `.editorconfig` 保存编辑器能够直接遵守的基础规则。具体工具配置仍由各工具自己的配置文件负责。

## 文件分类

### 普通文件

源码、Skill、提示词、配置和普通文档直接纳入格式化。

### Workspace 文件

`workspace/**` 中可编辑的文本同样纳入。格式工具只能调整排版，不能顺手改变业务含义。

### 故意写错的 Fixture

用于测试错误输入的 fixture 通过一份明确清单保留。清单逐文件说明为什么不能格式化或修正，不允许用“忽略整个 tests 目录”代替。

### 生成文件

生成文件应修改生成器后重新生成。不得在产物上手工修补，再让生成器继续输出旧格式。

### 原始引用

外部 PRD 原文、日志片段、HTTP 响应和用于复现问题的文本可以保留原样，但需要在文件中清楚标出引用边界。格式与中文检查跳过引用内容。

## 公共命令

```text
kata workspace format
kata workspace format --dry-run
kata workspace check
kata workspace check --format json
```

`format` 只做能够安全重复的机械调整。`check` 汇总格式、编码、链接、引用、Skill 结构和项目约定。两者都输出处理数量、跳过数量、失败数量和文件路径。

Claude、Codex 或其他平台的 hook 可以提前提醒，但不承担最终检查。公共 CLI 和 CI 才是每个平台都能重复执行的入口。

## 中文写作准则

### 准确

- 不改变原意、条件、范围和完成标准；
- 技术字段、命令和文件名逐字保留；
- 无法确认的内容不做推断；
- PRD、页面和源码互相不一致时，列出分歧并交给用户决定。

### 清楚

- 先说要做什么，再说原因；
- 一段只表达一件事；
- 主语、动作、输入和结果尽量完整；
- 例外紧跟在对应规则之后，不放到远处补充；
- 完成、未完成、部分完成使用明确含义。

### 自然

- 使用日常、克制的书面中文；
- 避免为了显得严谨而反复堆叠“必须、严禁、不得”；
- 避免生硬的复合名词、口号式标签和不符合中文习惯的抽象说法；
- 根据上下文使用“以当前页面为准”“参考材料”“运行结果”“缺少的信息”“暂时无法继续”等说法；
- 不把英文名词随意翻译成陌生的中文，也不在一句话中堆满缩写。

机器字段可以继续使用英文，但只出现在代码或字段说明中：

```text
source_ref
run_id
schema_version
```

普通叙述使用自然的中文说明其含义。

## 自动检查与人工复核

自动检查可以发现：

- 禁用表达；
- 同一段连续出现过多“必须、严禁、不得”；
- 过长句子；
- 中英文标点混用；
- 重复段落；
- 标题层级、列表和表格错误；
- 失效链接和错误相对路径。

自动程序只报告问题，不直接替换可能改变含义的词语。独立审阅者负责判断内容是否准确、清楚、自然。

核心 Skill、公共 prompt 和项目入口文档需要逐份复核。普通历史文件可以分批审阅，但每批都要保留改动清单和抽样结果。

## 历史内容修正

内容修正前先读取最新 PRD、当前页面和相关源码。

### 可以直接修正

- 明显的错别字、断句和标点错误；
- 已能从三类材料共同确认的旧菜单名、字段名和流程；
- 已失效的命令、路径和链接；
- 重复、矛盾且已有明确现行写法的说明。

### 需要用户决定

- PRD、页面和源码给出不同答案；
- 历史用例描述了当前环境无法重现的行为；
- 修改会改变用例范围、优先级或预期结果；
- 无法判断某份历史资料是否仍有业务价值。

每项内容修正记录：

```text
文件与位置
原文
修改后的文字
修改原因
参考的 PRD、页面或源码位置
尚未解决的分歧
```

## 提交拆分

按照以下顺序提交：

1. 工具配置与公共命令；
2. 纯格式调整；
3. Skill 与提示词表达调整；
4. Workspace 内容修正；
5. 生成文件重新生成；
6. 待确认项记录。

纯格式提交不得混入含义变化。内容修正提交需要在说明中列出范围。

## 检查

- 全部目标文件能被对应工具读取；
- `kata workspace check` 退出 0；
- 格式化连续执行两次，第二次没有 diff；
- fixture 清单中的每个排除项都有原因；
- 生成器重新生成后没有额外格式变化；
- 核心 Skill 的中文复核全部完成；
- Workspace 内容修改都有记录；
- 未跟踪文件没有被修改；
- 最终 `git diff --check` 通过。

## 完成标准

- 不再依靠 Claude 专属 hook 才能保持格式；
- Markdown、YAML、Python、Shell、XML 和 Workspace 进入正式检查；
- 项目没有宽泛到失去意义的格式排除目录；
- 格式化稳定、可重复；
- 生硬、重复和含糊的提示词已经重写；
- 能够确认的历史错误已经修正；
- 仍有分歧的内容进入待确认清单，没有被擅自改写。
