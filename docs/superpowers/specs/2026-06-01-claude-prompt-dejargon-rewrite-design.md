# 设计：.claude 提示词去黑话 + Opus 4.6 标准重写

- 日期：2026-06-01
- 状态：设计已批准，待 writing-plans 出实施计划
- 校准基准：本机 `functional-test-case-writer` skill（Opus 4.6 写作）

---

## 1. 背景

`.claude` 下的提示词经多个模型反复迭代后，混入两类问题：

1. **GPT 翻译腔 / 抽象黑话**：忠实度、沉淀、锚点、闭环、心智、抓手、颗粒度等。无功能含义，只增加阅读成本，且一眼能看出不是 Opus 写的。
2. **未验证的冗余规则**：上月在 Codex 用 `/goal` 让模型读自己的思维调用链、针对用例生成与 Playwright 脚本生成自迭代出来的一批规则。未经用户验证，实际冗余、可删可并。集中在 `case-draft`、`playwright-automation` 两个技能。

目标是把 `.claude` 全树的提示词拉回 **Opus 4.6 的写作标准**——以本机 `functional-test-case-writer` 为校准基准。

## 2. 目标

1. 全面去黑话、平实化重写，**语义不变**。
2. 删除或合并未验证的冗余规则；删改前先出清单交用户审。
3. 通篇达到 4.6 标准：**具体到无法误解、规则可机械检测、无黑话、无中英夹杂**。

## 3. 范围

**改写（In）：**

- `.claude/skills/**`（9 个技能的 SKILL.md / phases / references / prompts / rules）
- `.claude/rules/**`
- `.claude/prompt/**`
- 根 `CLAUDE.md`、`.claude/rules/project-workflow-rules.md`
- `INSTALL.md`（若含提示词文案）

**不动（Out）：**

- `.claude/scripts/**` 的代码逻辑
- 测试断言的业务含义
- `.claude/hooks`、`.claude/plugins`（第三方）

## 4. 4.6 校准基准

基准文件：`/Users/poco/.cc-switch/skills/functional-test-case-writer/`（`SKILL.md` + `references/anti-patterns.md` + `references/test-data-examples.md`）。

重写时对标的 4.6 DNA：

- **概念立刻落到例子上，具体到无法误解**——从不说「填写有效数据」，只说「输入『因业务集成需要…』（34 字符，满足 0-2000 字符限制）」。提示词本身和它要求的产物一样具体。
- **靠对照教学**——满篇「正确写法 / 错误写法（禁止）」「错误示例 → 修复后」。
- **禁令可机械检测**——不写「别写性能测试」，写「禁止出现『并发』『响应时间』『负载』『吞吐』等词」。能 grep 的规则才会被遵守。
- **判断变清单**——「是/否」自检 + 每项「通过标准」。
- **量化阈值**——用数字（次数、字符数、条数），不用「适当/尽量」。
- **结构即流程**——每节一个职责，顺序就是干活的顺序，零装饰。
- **SKILL.md 精炼，海量具体例子下沉 `references/`**。
- **雅是结果不是目的**——把「信（准确）」「达（清楚）」做到极致后，优雅自然浮现，不靠修辞堆砌。

一句话：**4.6 的优雅 = 具体到无法误解 + 用对照和清单把「判断」变成「可检测的动作」。**

## 5. 改写准则（唯一标尺）

本节是整个重写的唯一标尺和术语来源，保证 9 个技能用词一致。落地时先把它整理成独立的「改写准则」文档。

### 5.1 减法：黑话 → 平实（种子表，落地补全）

| 黑话 | 改成 |
|---|---|
| 忠实度 | 按语境：「步骤要真做、断言要断真实业务结果」 |
| 沉淀 | 记录 / 保存 / 写入 |
| 锚点 | 入口 / 定位点 / 起点 |
| 闭环 | 完整跑完 / 处理到底（常是凑词，可直接删） |
| 心智 | 删，或换「用户预期」 |
| 抓手 / 赋能 / 颗粒度 | 删，换具体说法 |
| 对齐 | 对账 / 核对 / 保持一致 |
| 收敛 | 缩小范围 / 定位到唯一 |
| 漂移 | 偏离 / 变了（product drift → 产品行为变了） |
| surface 假通过 / surface 契约测试 | 表面通过（没验业务）/ 只测页面表层不测业务结果 |

**保留术语白名单（有功能，不动）：** `证据`、`quality-gate`、`handoff`、`locator`、`fixture`、`session`、`preflight`、`spec`、`hard_rule`、`幂等`、`对账`（reconcile 固定译法）、英文 phase id（`case-normalize` 等）、Commit type。改了反增理解成本。

### 5.2 冗余 / 未验证规则判定（命中即标「拟删 / 拟合并」，过目后才动）

- **重复**：与同技能另一条表达同一约束 → 合并。
- **空泛防御**：只喊「确保 / 必须 / 严格」却无具体动作或判定条件，删掉不影响任何已有行为 → 删。
- **自指元规则**：Codex 自迭代出的「如何思考 / 如何保证质量」抽象条款，无可执行落点 → 删。
- **过度细化**：一个简单约束被拆成多条近义条款 → 合并。
- **保留**：有明确触发条件 + 明确动作 / 禁止项 + 对应到真实产物或测试的规则。

判断偏保守：吃不准就合并不删除；边界情况在审计清单标出来交用户定。

### 5.3 加法：信雅达正向准则（4.6 校准版）

1. **不抽象**：每条规则尽量给一个真实例子或可判定标准；吃不准就落到 `references/`。
2. **对照教学**：关键禁令配「对 / 错」两面，而非单向命令。
3. **禁令可检测**：能列举的就列举（禁用词、具体反模式），不留「别做坏事」式空话。
4. **判断变清单**：质量门禁 / 自评写成「是 / 否 + 通过标准」。
5. **量化**：阈值用数字（次数、字符数、条数），不用「适当 / 尽量」。
6. **信是红线**：**绝不为了优雅捏造 runtime 里不存在的例子、字段或数据**——kata 规则直接驱动真实执行，这点比 4.6 更要守。
7. **雅自然成**：把 1-6 做到位，优雅是结果；不为对仗、不为押韵单独加工。

**示例（4.6 式重写，对照感受标准）：**

> 原：覆盖忠实度：每条 expected_visible_result 必须断言为真实业务结果并真跑通。
>
> 4.6 式：每条 expected_visible_result 都要断言到真实业务结果，并真跑通过。
> - 对：导出类用例 → 断言下载文件存在、行数与列表一致。
> - 错：导出类用例 → 只断言「点击后无报错」或「按钮可见」。
> - 自检：这条断言失败时，是否真能说明业务坏了？不能，就是弱断言。

### 5.4 底线

- **语义不变（P0）**：每条规则改写后，「要求做什么 / 禁止做什么 / 触发条件」必须逐条等价；吃不准标出来问用户，绝不擅自放宽或收紧。
- **信是红线**：不为优雅捏造不存在的例子 / 字段 / 数据。
- **行数约束**：SKILL.md 守 lint 行数上限，具体内容（对照例子、禁用词清单、自检项）下沉到各技能 `references/`——这正是 4.6 自己的做法。

## 6. 工作流（detached worktree）

按项目规则在 detached worktree 内工作，四阶段推进：

**Phase 0 · 准则定稿**
把 §5 整理成独立的「改写准则」文档，作为整个重写的唯一标尺和术语来源。

**Phase 1 · 全量审计（产「审计清单」，先交用户审）**
扫描范围内全部文件，产出每文件改动清单，两栏：

- **黑话命中**：逐处列出命中的黑话词 + 拟改写法。
- **冗余 / 未验证规则**：逐条列出拟删 / 拟合并的规则 + 原因（对应 §5.2 哪条判定），重点 `case-draft`、`playwright-automation`。

这份清单是**审查闸门**——尤其规则删除，用户过目点头后才进 Phase 2。

**Phase 2 · 分技能落地（worktree 内）**
按技能逐个重写：SKILL.md 保持精炼（只留规则），把「对 / 错对照、禁用词清单、自检项」这类具体内容下沉到该技能 `references/`。**改一个技能立刻跑该技能相关测试**，绿了再下一个。每技能一个 commit。

**Phase 3 · 验证 + 合并**
`check:skills` + `bun test` 全绿；改过的 `description` 用 codex-companion 裸输入实跑触发链，diff transcript 确认触发没漂；hard_rules 改动同步更新 SHA / COUNT 基线。全绿后 `git merge --no-ff` 回 main、push、清理 worktree。

## 7. 产物清单

1. 改写准则文档（标尺）
2. 审计清单（可审，含拟删 / 拟合并规则）
3. 重写后的 `.claude` 全树提示词
4. 验证报告（跑了哪些测试、结果、触发链实跑结论、SHA 基线变更）

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **触发链漂移**（改 description 后 skill 触发不准） | 改后用 codex-companion 裸输入实跑每个 skill 触发链 + `check:skills`；RED/GREEN 对比 |
| **SHA 基线测试红**（case-draft 等 hard_rules 有基线） | hard_rules 改动**同一改动内**更新回归测试 COUNT + SHA，`bun test` 验证 |
| **lint 红线**（frontmatter 白名单 / 行数上限 / 禁装饰标记） | 守行数上限，具体下沉 `references/`；跑相关 lint 测试 |
| **语义漂移**（改写悄悄改了规则效力） | 每条 hard_rule 改完做「语义等价」自检（要求 / 禁止 / 触发条件逐条对照）；吃不准标出来问用户 |
| **误删有用规则** | 审计清单先交用户审；偏合并不偏删除；worktree + git 全程可回滚 |
| **跨技能术语不一致** | 准则文档 + 对照表是唯一术语来源 |

## 9. 验证与成功标准

**验证命令：**

- `bun run check:skills`（runtime 契约）
- `bun test`（全量）+ 受影响 `bun test .claude/scripts/_shared/tests/<area>`
- codex-companion 裸输入实跑触发链（改过 description 的技能）

**成功标准：**

1. 对照表里的黑话词全树清零（grep 命中为 0，或保留项有明确理由）。
2. 通篇读起来到 4.6 标准——具体、可检测、无黑话、无中英夹杂。
3. 拟删 / 拟合并的冗余规则全部经用户点头后处理完。
4. `check:skills` + `bun test` 全绿；改过的 description 触发链实跑验证通过。
5. **语义等价**：没有任何规则的实际效力在未经用户同意下被改变。
