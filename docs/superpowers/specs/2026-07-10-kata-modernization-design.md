# kata 现代化改造总设计

**日期**：2026-07-10  
**状态**：设计已确认，等待实施计划  
**基准**：[Superpowers v6.1.1](https://github.com/obra/superpowers/tree/v6.1.1)

## 目标

这次改造要让 kata 的 Skill、命令行工具、项目文档和历史资料形成一套清楚、稳定、可检查的体系。重点不是把现有文件换个位置，而是消除以下长期问题：

- Skill 正文以 Claude 为中心，其他平台依靠软链和临时翻译才能使用；
- 路由说明散落在入口文档、Skill 描述和平台适配文件中，容易互相偏离；
- CLI 的参数、输出、退出码、运行目录和数据结构没有统一；
- Markdown、YAML、Python、Shell 与 `workspace/**` 没有进入同一套格式检查；
- 旧命令、重复提示词、运行产物和历史副本缺少明确的保留规则；
- 提示词虽然严厉，却常用生硬、重复的表达，读起来费力，也不利于长期维护。

## 已确认的选择

| 事项 | 选择 |
| --- | --- |
| Skill 基础 | 采用 Open Agent Skills 的通用目录和渐进加载方式 |
| Skill 存放 | 根目录只保留一份 `skills/`，不再以 `.claude/skills` 为中心 |
| 平台交付 | 各平台分别安装插件，平台目录只负责发现、启动和工具说明 |
| 路由 | 直接使用 Skill 的 `name`、`description` 和正文边界，不建立独立 Router |
| 兼容方式 | 一次性切换，不保留旧命令、旧字段或旧目录的长期兼容层 |
| 运行验证 | Codex 真实安装和运行；Claude、Reasonix、Hermes 只做结构检查 |
| CLI | 只保留 `kata` 一个公开入口，原 `dtstack-cli` 能力并入命令组 |
| 用例文件名 | Markdown 与 XMind 使用同一个、经过清理的需求名称 |
| 格式范围 | 所有受版本控制的可编辑文本都纳入，包括 `workspace/**` |
| 内容修正 | 可以修正历史错误；无法从 PRD、页面和源码共同确认时交给用户决定 |
| 长任务方式 | 不使用 Goal，按 Superpowers 的完整流程推进 |
| 执行方式 | 主线程掌握设计，子代理逐项实现和复核；只并行互不影响的工作 |

## 目标结构

```text
skills/                         # 唯一可编辑的 Skill 正文
  using-kata/
  case-draft/
  playwright-automation/
  ...

.codex-plugin/                  # Codex 插件说明
.claude-plugin/                 # Claude 插件说明
.reasonix/                      # Reasonix 薄适配
.hermes/                        # Hermes 薄适配

packages/                       # 平台无关的 CLI、数据结构与公共代码
scripts/package/                # 各平台打包脚本
tests/runtime/                  # 安装、发现与实际调用检查
docs/superpowers/specs/         # 设计文档
```

业务 Skill 不出现 `AskUserQuestion`、`TodoWrite`、`Task` 等平台工具名。它们只写“询问用户”“维护计划”“派出子代理”等动作。`using-kata` 根据当前平台加载对应说明。

## 子项目

### 1. CLI 与产物

统一公开命令、帮助、参数、文本输出、JSON 输出、退出码、schema、metadata、用例文件名和运行目录。详细设计见 [CLI 与产物设计](2026-07-10-kata-cli-design.md)。

### 2. Skill 与插件

建立根级 `skills/`，统一 Skill 写法和平台适配，重新设计所有路由描述，并重点重构 `case-draft` 与 `playwright-automation`。详细设计见 [Skill 与插件设计](2026-07-10-kata-skills-design.md)。

### 3. 格式与内容

为所有文本文件选择固定工具，统一编码和排版；同时整理中文表达，校正能够确认的历史错误。详细设计见 [格式与内容治理设计](2026-07-10-kata-content-governance-design.md)。

### 4. 历史清理

迁移旧目录和旧产物，删除重复、失效或可重新生成的文件，并保留清楚的处理记录。详细设计见 [历史文件清理设计](2026-07-10-kata-cleanup-design.md)。

## 实施顺序

实际实施按依赖推进：

1. 保存当前行为样例，建立改造前基线；
2. 统一 CLI、schema、metadata、用例文件名和运行目录；
3. 建立根级 `skills/` 和各平台插件；
4. 重写全部 Skill，重点完成两个核心 Skill；
5. 格式化并校正文档、用例和项目知识；
6. 迁移并删除旧命令、旧目录和重复文件；
7. 在干净环境安装 Codex 插件，重新执行完整流程。

CLI 先于 Skill 内容重写，是因为 Skill 会大量引用命令、字段和文件路径。先把这些接口稳定下来，可以避免同一批提示词反复改动。

## 实施方法

采用以下 Superpowers 流程：

```text
brainstorming
→ writing-plans
→ subagent-driven-development
→ verification-before-completion
```

主线程负责设计、任务顺序、公共接口和最终整合。每项边界清楚的工作交给新的执行子代理，再由新的审阅子代理检查。共享入口、公共 schema、`using-kata` 和最终迁移必须串行完成。

适合并行的工作只有：只读盘点、互不重叠的简单 Skill、独立测试和分目录检查。多个代理不得同时修改同一公共文件。

## 迁移方式

最终不保留兼容层，但迁移过程需要可检查、可恢复：

1. 在隔离 worktree 中建立新结构；
2. 用 `--dry-run` 预览文件名、metadata 和历史内容迁移；
3. 先更新引用，再移动或删除旧文件；
4. 将格式化、内容修正、结构迁移和删除拆成独立提交；
5. 新插件真实安装并通过检查后，才切换正式入口；
6. 当前主工作树中用户已有的修改和未跟踪文件不参与自动迁移。

## 完成标准

### 范围已确认

- 设计文档中没有未填写的占位项或含糊的延期表述；
- 每项无法自动决定的业务内容都进入待确认清单；
- 实际执行范围与最终报告中的表述完全一致。

### Skill 设计正确

- 每个 Skill 都有明确的触发、排除、转交和信息不足样例；
- Skill 正文保持平台无关，并按需加载脚本和参考资料；
- 能由程序检查的规则不再依赖提示词反复提醒；
- 修改一个 Skill 后，不会要求同步修改多份正文。

### 真实运行完成

- Codex 从干净环境安装插件，并真实触发全部业务 Skill；
- `case-draft` 从需求材料生成同名 Markdown 和 XMind；
- `playwright-automation` 执行目标 `full.spec.ts`，生成 Allure 结果，并在平台留下相应业务记录；
- CLI 生命周期从功能目录建立一直运行到交付文件生成；
- 最终报告列出命令、退出码、通过数、失败数、跳过数和文件路径。

### 中文自然准确

- 原意、条件和完成标准没有被改坏；
- 读者第一次阅读就知道要做什么、何时停止、出错后怎么办；
- 句子简洁自然，不堆叠口号、禁令和生硬术语；
- 自动检查负责发现重复、长句和标点问题，独立审阅者负责判断表达是否妥帖。

## 不在范围内

- 不为 Claude、Reasonix 或 Hermes 宣称真实端到端通过；
- 不保留旧 CLI、旧 schema 或旧目录的长期兼容入口；
- 不在无法核对时自行修改业务含义；
- 不删除当前主工作树中用户尚未提交的文件；
- 不把结构检查通过表述成真实业务流程通过。
