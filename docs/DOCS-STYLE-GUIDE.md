# Kata 文档与中文写作规范

## 目标

文档首先帮助读者完成任务，其次才解释内部设计。文字应简洁、自然、明确，不用堆叠抽象名词制造严谨感。

## 结构

- 一个文件只有一个主要目的。
- 标题按 `#`、`##`、`###` 递进，不跳级。
- 开头说明适用对象、能完成什么、最短入口。
- 命令先给可复制示例，再解释参数。
- 行为变化同步更新 README、README-EN、INSTALL 和 CHANGELOG。
- 用例文档不纳入通用文档润色；它们由用例 Schema 与对应 Skill 管理。

## 中文

- 一句只表达一个判断。
- 主语和动作明确，少用“进行、实现、完成对……的”一类空壳结构。
- 英文术语第一次出现时给出中文含义，后文选择一种写法。
- 文件名、命令、字段名保留代码格式；普通概念使用中文。
- 不把内部架构口号直接写给使用者；改成明确的对象、动作和结果。

推荐替换：

| 避免 | 使用 |
| --- | --- |
| 中英混排的能力名称 | 可追溯的测试流程 / 可复用的测试能力 |
| 强调某运行环境地位的内部说法 | 主要实现 / 默认运行目录 |
| 把共用代码写成口号 | 共用运行工具 / 共用代码 |
| 强调信息等级 | 当前采用的来源 / 已核对内容 |
| `SourceRef`（面向用户） | 来源记录 |
| 闭环 | 完成检查并记录结果 |
| 阻塞（泛用） | 待确认 / 暂不能生成最终版 |
| 赋能 | 支持 / 帮助 |
| 沉淀 | 记录 / 整理 / 保存 |

内部字段名可以保留英文，例如 `source_ref`；正文不必把字段名变成口号。

## Markdown

- 表格必须有表头，列数一致；内容过长时改用小节，不把整段文字塞进单元格。
- 代码块标明语言；命令块只放可执行内容，说明写在块外。
- 列表项语法和句末标点统一。
- 链接文字说明目标，不使用“点击这里”。
- Mermaid 只在图比文字更清楚时使用；流程少于五步优先用短列表。
- README 不用手写能力数量。由 manifest 生成，或在 CI 中核对目录与表格。

## README 建议顺序

1. 项目一句话说明。
2. 最短安装与第一个可运行命令。
3. 能力清单（由 manifest 生成）。
4. 目录和数据边界。
5. Claude 与 Codex 的差异。
6. 开发、验证和贡献方式。
7. 安全说明与 License。

不要在 README 同时维护安装手册、完整 CLI 参考、Skill 内部流程和迁移历史；分别链接到对应文档。

## 中英文一致性

中文文档是行为主稿时，英文版从同一结构生成或逐节对应。CI 至少核对：

- Skill 名称与数量。
- 命令名。
- 目录路径。
- 配置文件位置。
- 安全要求和退出码。

翻译可以自然，不得改变行为合同。
