# Case Draft

把需求整理成可复核、可继续校准的测试用例。优先完成有把握的部分；缺少信息时区分“影响最终范围”和“只影响局部措辞”，不要把所有缺口都升级为阻塞。

## 接受的输入

- PRD、Markdown、Lanhu/Axure 链接、截图、设计稿或用户描述。
- 已有 `archive.md`，用于补充或质量复核。
- feature 目录或能唯一定位 feature 的项目、模块和版本信息。

详细字段和目录见 `references/input-output-contract.md`。

## 路由

按用户要完成的动作判断，不按文件扩展名判断：

- 新建、补充、复核测试用例：本 Skill。
- 只转换 MD/XMind/CSV/JSON 格式：`case-edit`。
- 把已有用例实现成 UI 自动化：`playwright-automation`。
- 根据单条缺陷生成 Hotfix 回归用例：`case-hotfix`。

## 工作方式

1. **定位目标**：从明确输入或项目配置定位 project、feature 与输出目录。只有多个候选无法消歧时才询问用户。
2. **整理需求**：列出功能目标、规则、角色、状态变化、异常条件和待确认项，并保存来源记录。不要编造需求编号、版本、菜单名或环境差异。
3. **确定范围**：当一个答案会明显改变测试集合、目标版本或交付目录时，一次性提出必要问题；其他缺口写为 `待确认`，继续生成初稿。
4. **起草与复核**：生成主路径、异常、边界、权限、数据与回归场景。优先级按风险决定，不设固定比例。
5. **校准页面内容**：有截图、DOM 或可访问环境时，校准菜单、按钮、字段和提示语；没有时保留自然的占位说明，不把需求初稿伪装成已校准版本。
6. **检查与交付**：运行可用的结构检查。最终版生成 XMind；仍有关键缺口时交付草稿和待确认清单。

模型可根据任务规模合并步骤、使用并行检查或子代理；不要固定模型名称和代理拓扑。

## 成熟度

- `requirements-draft`：基于需求的初稿，允许页面文案待校准。
- `ui-calibrated`：菜单、字段和按钮已与目标环境或截图核对。
- `executable`：关键前置、步骤和预期可执行，结构检查通过。

## 不可违反的规则

- 不编造外部编号、版本、租户、菜单文案、可选值或系统行为。
- 不因缺少非关键细节而停止整个任务；用清楚的 `待确认` 标记隔离不确定部分。
- 不把历史用例当成当前行为的唯一依据。发现冲突时同时记录差异，并优先采用用户指定或当前环境已核对的内容。
- 已有用例使用稳定 `case_id`；更新时保留 ID。需要重建时先输出映射和差异。
- 最终 `archive.md` 中的用例数、frontmatter 和 XMind 节点数必须一致。
- 机械格式、字段和引用检查交给 CLI/Schema；内容评审只判断覆盖、可执行性和表达质量。

## 交付状态

- `draft`：已生成初稿，仍有待确认项。
- `ready`：输入完整，结构检查通过，可进入自动化或评审。
- `blocked`：缺少目标目录、必要权限或会改变整个范围的关键信息，当前无法继续。
- `failed`：命令或生成过程失败。

最终回复说明状态、范围、文件路径、检查命令与未解决项。不要用“全部完成”代替具体范围。

## 质量标准

读取 `references/quality-rubric.md`。只有在需要核对输入、目录或字段时才读取 `references/input-output-contract.md`。
